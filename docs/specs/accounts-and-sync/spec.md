# 로그인과 계정별 서버 저장

헬스 일지에 처음 들어가면 로그인 화면이 나오고, 아이디와 비밀번호로 가입하거나 로그인한 사람만 앱을 쓸 수 있습니다. 메일 인증은 하지 않습니다. 운동 기록은 계정별로 서버에 저장되어, 어느 기기에서 로그인해도 같은 기록이 보입니다.

이 스펙은 [gym-log-core](../gym-log-core/spec.md)가 "제외"로 둔 로그인, 계정, 서버 저장을 다룹니다. 기록 입력, 비교, 달력, 차트 같은 동작은 gym-log-core가 그대로 정하고, 이 스펙은 "누가 로그인했는지"와 "기록을 어디에 저장하는지"만 바꿉니다. 두 스펙이 어긋나는 부분(저장소, 제외 범위)은 이 스펙이 우선합니다.

## 사용자에게 보이는 결과

- 로그인하지 않은 채 어느 주소로 들어와도 로그인 화면이 나옵니다.
- 로그인 화면에서 아이디와 비밀번호로 로그인하거나 회원가입합니다.
- 로그인하면 기록 화면으로 가고, 기록, 달력, 차트를 지금처럼 씁니다. 모든 화면에서 로그아웃할 수 있습니다.
- 내가 입력한 기록은 내 계정에만 보이고, 폰과 PC 어디서 로그인해도 같습니다.
- 새로고침하거나 다시 방문해도 로그인이 유지됩니다.
- 처음 가입한 계정은 기록이 없는 상태로 시작합니다.

## 범위

### 포함

- 로그인 화면(로그인과 회원가입 전환), 로그아웃.
- 로그인하지 않은 상태의 접근 제한(모든 화면).
- 운동 기록의 계정별 서버 저장과, 본인 기록만 읽고 쓰고 지울 수 있는 접근 규칙.
- Vercel에 배포한 주소에서 같은 동작.

### 제외

- 브라우저에 이미 저장된 기록을 계정으로 옮기는 일(사용자가 옮기지 않기로 정함).
- 비밀번호 찾기·재설정, Google 등 소셜 로그인, 실제 이메일을 받는 가입.
- 친구 추가와 친구 간 기록 공유.
- 네트워크가 없을 때 기록을 쌓아 두었다가 나중에 올리는 기능.
- 프로필 화면, 계정 삭제, 이메일·비밀번호 변경.

## 동작

### 로그인 화면

- 입력은 아이디와 비밀번호입니다. "로그인"과 "회원가입"을 오가는 전환이 있고, 같은 화면에서 처리합니다.
- 아이디는 영문, 숫자, 밑줄(`_`)로 3~20자입니다. 대소문자는 구분하지 않고(소문자로 맞춰 저장), 앞뒤 공백은 지웁니다. 한글, 이메일 모양, 공백이 든 아이디는 받지 않습니다.
- 비밀번호는 6자 이상입니다.
- 회원가입이 성공하면 바로 로그인된 상태가 되어 기록 화면으로 갑니다(메일 인증 없음).
- 오류는 입력 칸 근처에 사람이 읽는 문장으로 보여줍니다. 아이디 또는 비밀번호가 틀렸을 때, 이미 쓰는 아이디일 때, 아이디 규칙에 맞지 않을 때, 비밀번호가 너무 짧을 때를 구분합니다. 로그인 실패는 아이디와 비밀번호 중 무엇이 틀렸는지 밝히지 않습니다.
- 서버에 요청하는 동안은 버튼을 눌러도 중복 요청이 가지 않도록 막고, 진행 중임을 보여줍니다.
- 로그인 화면에는 앱의 탭과 "오늘 한 운동" 목록이 나오지 않습니다.

### 접근 제한과 세션

- 로그인하지 않은 상태에서 기록, 달력, 차트 어느 주소로 들어가도 로그인 화면이 나옵니다. 로그인 화면 외에 보이는 기능은 없습니다.
- 로그인하면 기록 화면으로 갑니다.
- 로그인은 이 브라우저에서 유지되어, 새로고침이나 다시 방문해도 다시 입력하지 않습니다.
- 로그인한 상태에서 로그인 화면 주소로 들어오면 기록 화면으로 보냅니다.
- 로그아웃하면 로그인 화면으로 가고, 이후 이 브라우저에서 이전 계정의 기록이 보이지 않습니다.

### 기록 저장

- gym-log-core의 모든 기록 동작(세트 입력, 추가, 삭제, 날짜 선택, 비교, 달력 수정, 차트)은 그대로이고, 저장 위치만 서버입니다.
- 입력하는 즉시 저장하는 흐름은 유지합니다. 서버 응답을 기다리는 동안에도 입력 칸이 막히지 않고, 저장이 끝나지 않았거나 실패하면 그 사실을 눈에 띄지 않게 알려 줍니다.
- 저장에 실패하면(네트워크 없음, 서버 오류) 실패했다는 안내를 보여주고, 사용자가 다시 시도할 수 있습니다. 실패한 값이 저장된 것처럼 보이면 안 됩니다.
- 기록을 불러오는 동안에는 빈 화면이 아니라 불러오는 중임이 보이고, 불러오지 못하면 안내와 다시 시도를 보여줍니다.
- 다른 계정의 기록은 어떤 경로로도 읽거나 고칠 수 없습니다. 이 제한은 화면이 아니라 서버가 지킵니다.
- 무게 단위(kg/lb)와 다크모드는 계정이 아니라 이 기기 설정으로 둡니다(지금처럼 브라우저에 저장).

### 기존 브라우저 기록

- 이전에 이 브라우저에 쌓인 기록은 옮기지 않습니다. 로그인한 뒤에는 서버의 기록만 사용하고, 브라우저의 예전 기록은 읽지도 지우지도 않습니다.

## 인수 기준

1. 로그인하지 않고 `/`, `/calendar`, `/chart`에 들어가면 모두 로그인 화면이 나오고, 앱 탭과 기록 화면 내용은 보이지 않는다.
2. 새 아이디와 비밀번호로 회원가입하면 곧바로 기록 화면으로 가고, 기록은 비어 있다.
3. 로그인 화면에서 틀린 아이디나 비밀번호, 이미 쓰는 아이디, 규칙에 맞지 않는 아이디, 너무 짧은 비밀번호는 각각 다른 안내 문장이 나오고, 아이디나 비밀번호 칸의 오류는 그 칸 근처에 나온다.
4. 요청이 진행되는 동안 로그인과 회원가입 버튼을 다시 눌러도 중복 요청이 가지 않는다.
5. 로그인한 뒤 새로고침하거나 브라우저를 닫았다 열어도 로그인이 유지되고 기록이 그대로 보인다.
6. 한 계정으로 입력한 기록을 다른 기기나 다른 브라우저에서 같은 계정으로 로그인하면 똑같이 볼 수 있다.
7. 같은 아이디는 대문자로 입력해도 같은 계정으로 로그인된다. 이어서, 계정 A로 입력한 기록은 계정 B로 로그인하면 기록 화면, 달력, 차트 어디에도 나타나지 않는다.
8. 로그아웃하면 로그인 화면으로 가고, 뒤로 가기나 주소 입력으로도 앱 화면이 보이지 않는다.
9. 로그인한 상태에서 로그인 화면 주소로 들어오면 기록 화면으로 간다.
10. 세트를 입력, 추가, 삭제하고 새로고침하면 그 변경이 서버에 반영되어 있다.
11. 네트워크를 끊고 세트를 입력하면 저장 실패 안내가 나오고, 연결을 되돌려 다시 시도하면 저장된다. 실패한 동안에는 저장된 것처럼 보이지 않는다.
12. 이전에 이 브라우저에 있던 기록은 새 계정에 나타나지 않는다.
13. Vercel에 배포한 주소에서도 1~10이 똑같이 동작한다.

## 확정된 제약과 이유

- 로그인과 저장은 Supabase(인증과 Postgres)를 쓰고, 배포는 Vercel에 합니다. 사용자가 정했습니다.
- 계정 구분과 기록 접근 제한은 서버가 지킵니다. 화면만 가리는 방식은 다른 계정의 기록을 막지 못하기 때문입니다.
- Supabase 주소와 공개 키는 코드에 넣지 않고 환경 변수로 둡니다. 로컬 개발과 Vercel 배포가 같은 방식으로 값을 받습니다.
- 브라우저로 내려가는 키는 공개용 키뿐이고, 관리자 권한 키는 브라우저에서 쓰지 않습니다.
- 일반 UI 구성은 [ui-composition](../../decisions/ui-composition.md)을 따릅니다. 로그인 폼은 shadcn의 Field 구성과 Card 등 기존 컴포넌트로 만들고 오류 문구는 공통 상태 표현을 씁니다.
- 세트 사이에 빠르게 기록해야 하는 경험 원칙(`PRODUCT.md`)에 따라, 서버 저장을 기다리느라 입력이 막히면 안 됩니다.
- 기록의 의미(같은 머신·종목·브랜드·모델 비교, 날짜별 기록)는 gym-log-core가 정한 그대로입니다. 모델은 workouts 테이블의 `model` 칸(빈 문자열 가능)에 저장하고, 하루에 하나라는 제한도 모델까지 포함한 (user_id, date, exercise, brand, model) 기준입니다. 모델이 생기기 전에 남긴 기록은 마이그레이션이 그 종목·브랜드의 첫 모델로 채웁니다.

## 가정(사용자가 뒤집을 수 있음)

- 로그인은 아이디로 하지만, 서비스(Supabase Auth)는 이메일을 신원으로 쓰므로 아이디에 고정된 꼬리(`@gymlog.app`)를 붙인 이메일 모양으로 저장합니다. 메일은 보내지 않고, 사용자에게 보이지도 않습니다. 이 꼬리를 바꾸면 기존 계정으로 로그인할 수 없습니다.
- 이 방식은 Supabase의 이메일 인증을 끈 설정을 전제로 합니다. 켜면 가입해도 로그인되지 않습니다.
- 서버가 이 꼬리를 받아 주는지는 실제로 가입해 봐야 알 수 있습니다. 받지 않으면 꼬리를 바꿉니다.
- 비밀번호 최소 길이는 서비스 설정의 기본값(6자)을 따르고, 화면에서도 같은 규칙으로 먼저 검사합니다.
- 무게 단위와 다크모드는 기기별 설정입니다. 다른 기기에서 로그인하면 그 기기의 설정이 적용됩니다.
- 로그인한 사용자의 표시는 화면 위쪽의 로그아웃 버튼만 둡니다. 이메일 표시나 프로필은 두지 않습니다.
- 로그인 화면은 따로 프로토타입을 만들지 않았고, 폭이 좁은 폰과 PC에서 한 단의 가운데 정렬 카드로 보여줍니다.

## 구현 전에 필요한 것(사용자가 준비)

- Supabase 프로젝트(지역은 서울 `ap-northeast-2` 권장)와 프로젝트 주소, 공개 키. 계정과 키는 사용자가 직접 만들고 알려 줍니다. 앱 쪽에는 이 값이 있어야 구현을 확인할 수 있습니다.
- Supabase에서 이메일 인증을 끄는 설정(가정 참고)과, 로컬 주소(`http://localhost:3000` 등)와 Vercel 배포 주소를 허용 주소로 등록하는 일.
- Vercel 계정과 프로젝트 연결, 환경 변수 등록. 배포는 사용자가 요청할 때 진행합니다.

## 건드리지 않는 영역과 이유

- 기록 입력, 비교, 달력, 차트의 동작과 화면: gym-log-core가 정한 대로 유지합니다. 이 작업은 저장 위치와 접근 제한만 바꿉니다.
- 친구 공유, 비밀번호 재설정, 소셜 로그인, 오프라인 기록: 사용자가 이번 범위에서 제외했거나 결정하지 않았습니다.
- `PRODUCT.md`: 이 작업은 제품 전제를 바꾸지 않고 오히려 "계정별 로그인과 개인 기록"을 이루는 쪽입니다. "지인들이 쓰는 서비스"와 친구 공유는 여전히 별도입니다.

## 보류한 항목

- 비밀번호 찾기·재설정: 아이디 계정에는 메일을 받을 주소가 없어서 비밀번호를 잊으면 복구할 수단이 없습니다. 복구가 필요해지면 실제 이메일을 받는 방식이나 관리자가 직접 재설정하는 방식을 따로 정합니다.
- Google 등 소셜 로그인.
- 네트워크가 약한 헬스장을 위한 오프라인 기록과 나중에 올리기.
- 친구 추가와 기록 공유(접근 규칙을 계정 단위에서 친구까지 넓히는 일).

## 남은 위험

- 가입 제한이 없고 아이디의 주인을 확인하지 않아서, 배포 주소가 알려지면 누구나 가입할 수 있습니다. 지인에게만 알려 주는 용도라는 전제입니다.
- 비밀번호를 잊으면 계정을 되찾을 방법이 없고, 나중에 이메일 재설정을 붙이기도 어렵습니다(보류 항목 참고). 아이디는 만든 뒤 바꿀 수 없습니다.
- 헬스장에서 신호가 약하면 저장이 실패할 수 있고, 오프라인 기록이 없어서 그 세트는 다시 입력해야 합니다.
- Supabase 무료 요금제는 한동안 접속이 없으면 프로젝트가 일시 정지될 수 있습니다. 정지되면 로그인과 기록이 모두 멈춥니다.
- 지금 브라우저에 쌓인 기록은 옮기지 않기로 해서, 이미 입력한 기록은 새 계정에서 보이지 않습니다.
- 로그인 화면은 프로토타입으로 검토하지 않았습니다. 화면 구성은 구현한 뒤 직접 보고 고쳐야 할 수 있습니다.
- 서버 저장으로 바꾸면 기록 입력이 네트워크 속도에 영향을 받을 수 있습니다. 입력이 막히지 않아야 한다는 조건으로 줄이지만, 실제 체감은 배포 후 확인해야 합니다.
